# 평가와 PR 전 검토 운영

평가는 작성 맥락이 없는 평가 에이전트(`analysis-evaluator`)가, PR 전 검토는 `pr-reviewer`가 한다. 메인은 이 스킬대로 부르고, 결과를 읽고, 다음 단계를 정한다. 메인이 직접 평가하거나 검토하지 않는다.

순서: 먼저 저장소에 정해진 검사(`.claude/harness/config.json`의 `check`)를 돌린다. 그다음 두 단계로 받는다.

1. 1단계: 같은 커밋에 평가와 PR 전 검토를 병렬로 부른다. 메인은 두 결과의 지적을 한 번에 고친다.
2. 2단계: 수정 커밋의 diff로 평가와 검토를 병렬로 한 번씩 다시 받는다.

평가 대상 파일을 바꾸지 않은 작업은 PR 전 검토만 같은 두 단계로 받는다.

역할: 평가는 루브릭(`.claude/rubrics/<이름>.md`)의 항목으로만 판정한다. 문서 사이의 정합을 누가 보는지는 루브릭의 R8 폐지 줄을 따른다. 두 에이전트가 같은 지적을 따로 내지 않게 하기 위해서다.

평가 대상 파일은 루브릭이 판정하는 파일이다: `docs/`, `src/`, `scripts/`, `analyses/`, `experiments/`, `artifacts/`, `tests/baseline/`(기준값 파일). 하네스 파일, CI 설정, 의존성 파일, 그 밖의 `tests/`, `.gitignore`는 평가 대상이 아니다.

플러그인의 PR 검사는 하네스 파일이 아닌 파일을 바꾼 PR에 평가 기록을 요구한다. 평가 대상 파일을 바꾸지 않았는데 이 검사에 막히면, 바꾼 파일을 입력으로 평가를 한 번 받는다. 이때 입력 파일 목록은 아래 "평가 대상 파일 모두"의 예외로, 바꾼 파일 전체다.

## 평가 부르기

지시문에 아래를 둔다. 평가 에이전트는 지시문에 없는 것을 모른다.

- findings 경로: `_workspace/findings/<작업>/r<N>.json`. 메인이 여러 결과를 합쳐 쓸 때도 `Write` 도구로 쓴다. 평가 기록이 `Write`에서만 남는다. 작업은 브랜치 이름 그대로이고 `/`는 하위 폴더가 된다. N은 그 폴더의 가장 큰 번호에 1을 더한 값이고 처음은 1이다. 단계마다 파일 하나다.
- 범위: 평가할 커밋(`git rev-parse HEAD`)과 입력 파일 목록(이번 작업이 바꾼 평가 대상 파일 모두). 바뀐 줄을 봐야 하면 diff를 파일로 저장해 그 경로도 넣는다. 평가 에이전트는 `git`을 돌리지 못한다. 2단계에서 볼 범위를 수정 diff와 직전 findings로 줄여도 입력 파일 목록은 줄이지 않는다. PR 검사가 이 목록으로 평가 뒤 바뀐 파일을 찾는다.
- 이미 확인한 사실: 메인이 돌린 검사 결과, 앞 단계 findings 경로. `experiment.md`를 바꾼 작업이면 질문과 설계 절을 더한 커밋과 `artifacts/<ID>/metrics.json` 첫 커밋의 순서(`git log`로 확인).
- 루브릭: `.claude/rubrics/<이름>.md`. 어느 항목에도 들지 않는 지적은 `item`을 `"new"`로 적게 한다.
- 심각도: `must`는 산출물이나 판정을 실제로 막는 것에만, 나머지는 `should`.
- 금지: 산출물 수정, findings 경로 밖 쓰기, 같은 파일 다시 읽기.

## PR 전 검토 부르기

`pr-reviewer`는 셸이 없다. 메인이 `git diff origin/main...HEAD`를 파일로 저장해 지시문에 그 경로를 넣는다. 지시문에는 단계, 이미 확인한 사실(돌린 검사와 결과, 2단계면 1단계 평가 findings 경로)을 함께 둔다. 2단계는 수정 커밋의 diff와 직전 지적만 넘긴다. 검토 결과는 답 메시지로 받는다. 평가와 검토의 단계별 판정, 지적 수와 주요 지적, 반영 커밋을 PR 첫 댓글 하나에 함께 남긴다.

## 멈춤

평가와 검토를 반복할수록 앞에서 고친 문장이 새 지적을 낳는다. 그래서 단계 수를 미리 정해 둔다.

1. 1단계 지적을 고칠 때는 심각도와 관계없이, 지적이 하나여도 그 문단을 다시 쓴다. 문장만 덧대면 2단계에서 새 지적이 생긴다.
2. 2단계 수정 diff는 앞뒤 문맥을 넓혀(`git diff -U15`) 저장한다. 고친 문장의 주변 문장까지 보게 하기 위해서다.
3. 1단계에 지적이 없으면 2단계 없이 멈춘다. 2단계에 must가 없으면 멈춘다. 남은 should는 고치지 않는다. 마지막 평가 뒤에 입력 파일을 바꾸면 PR 검사(`pr-stale`)가 막는다.
4. 2단계에 must가 있으면 고치고 수정 diff로 한 단계 더 받는다. 그 단계에도 must가 남으면 사용자에게 묻는다.

가리킨 곳의 내용은 그대로인데 절 번호만 바뀌어 끊긴 참조는 심각도와 관계없이 지적이 나온 단계에서 바로 고치고 BACKLOG로 미루지 않는다. 이 지적은 위 3·4번에서 단계를 더 돌릴 이유로 세지 않는다. 다만 2단계 뒤에 고쳐 PR 검사(`pr-stale`)에 막히면 바꾼 파일만 입력으로 평가를 한 번 받고, 이 평가는 단계 수에 세지 않는다.

평가나 검토를 거치지 않은 변경이 남았으면 사용자에게 묻는다.

멈춤에서 고치지 않은 should는 PR 본문과 `_workspace/BACKLOG.md`에 적고, 같은 종류의 다음 PR(작업이면 다음 작업 PR, 하네스면 다음 하네스 PR)에 넣어 처리한다.

2단계를 마쳤으면, 사용자에게 보고하기 전에 두 단계의 지적을 함께 본다. 공통 원인이 있는지, 원인을 직접 없앨 방안이 있는지를 함께 보고한다. 지적마다 덧대어 고치면 고친 자리에서 다음 지적이 나온다.

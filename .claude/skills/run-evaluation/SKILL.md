# 평가 운영

평가는 작성 맥락이 없는 평가 에이전트(`analysis-evaluator`)가 한다. 메인은 이 스킬대로 부르고, 결과를 읽고, 다음 라운드를 정한다. 메인이 직접 평가하지 않는다.

## 부르기

지시문에 아래를 둔다. 평가 에이전트는 지시문에 없는 것을 모른다.

- findings 경로: `_workspace/findings/<작업>/r<N>.json`. 메인이 여러 결과를 합쳐 쓸 때도 `Write` 도구로 쓴다. 라운드 기록이 `Write`에서만 남는다. 작업은 브랜치 이름 그대로이고 `/`는 하위 폴더가 된다. N은 그 폴더의 가장 큰 번호에 1을 더한 값이고 처음은 1이다.
- 범위: 평가할 커밋(`git rev-parse HEAD`)과 입력 파일 목록(이번 작업이 바꾼 산출물 파일 모두). 바뀐 줄을 봐야 하면 diff를 파일로 저장해 그 경로도 넣는다. 평가 에이전트는 `git`을 돌리지 못한다. 2라운드부터 볼 범위를 수정 diff와 직전 findings로 줄여도 입력 파일 목록은 줄이지 않는다. PR 검사가 이 목록으로 평가 뒤 바뀐 파일을 찾는다.
- 이미 확인한 사실: 메인이 돌린 검사 결과, 앞 라운드 findings 경로.
- 루브릭: `.claude/rubrics/<이름>.md`. 어느 항목에도 들지 않는 지적은 `item`을 `"new"`로 적게 한다.
- 심각도: `must`는 산출물이나 판정을 실제로 막는 것에만, 나머지는 `should`.
- 금지: 산출물 수정, findings 경로 밖 쓰기, 같은 파일 다시 읽기.

## 멈춤

평가를 반복할수록 앞 라운드에서 고친 문장이 새 지적을 낳는다. 그래서 라운드 수를 미리 정해 둔다.

1. must가 있으면 고치고 다음 라운드를 돈다. 지적이 하나여도 그 문단을 다시 쓴다. 문장만 덧대면 다음 라운드에 새 지적이 생긴다.
2. must가 없는 라운드가 나오면 그 라운드의 should를 한 번 반영하고 평가를 한 번만 더 돈다.
3. 그 평가에도 must가 없으면 멈춘다. 남은 should는 고치지 않고 PR 본문에 적는다. 마지막 평가 뒤에 입력 파일을 바꾸면 PR 검사(`pr-stale`)가 막는다.
4. 3라운드 뒤에도 must가 남으면 사용자에게 묻는다.

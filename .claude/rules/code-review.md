# Python 코드 기준

코드를 쓸 때와 리뷰할 때 이 기준으로 본다. 리뷰 지적에는 항목 번호(C1 등)를 붙인다.

## C1. 입력 검증은 경계에서 pydantic이나 명시적 예외로 한다

- 경계는 프로그램 밖에서 들어오는 값이다: 설정 파일(`config.yaml`, `splits.yaml`), JSON 상태 파일(`state.json`, `manifest.json`), DuckDB에서 읽은 실행 설정, CLI 인자, 외부 명령의 출력.
- 경계의 값은 pydantic 모델로 한 번 검증하고, 안쪽 함수는 검증된 타입을 받는다. 파일에서 읽어 `Cls(**data)`로 만드는 값은 pydantic 모델로 둔다.
- 모델로 표현하기 어려운 조건(파일 사이의 관계, 해시 대조)은 `raise <구체적 예외>(무엇이 어떻게 틀렸는지)`로 알린다. `assert`로 입력을 검증하지 않는다. `python -O`에서 사라지고, 실패 메시지가 원인을 말하지 않는다.
- `assert`는 코드 안의 가정(앞 단계가 보장한 불변식)을 적는 데 쓸 수 있다. 한 함수에 `assert`가 여럿 쌓이면, 그 가정을 타입이나 모델로 옮길 수 있는지, 그 상황을 만드는 호출처가 실제로 있는지 본다.
- 지적할 것: 한 함수에 몰린 `assert`, 입력 검증에 쓴 `assert`, 경계 안쪽에서 같은 값을 다시 검사하는 곳, 그 상황을 만드는 호출처가 없는 검사.

## C2. 상태값마다 늘어지는 if-elif는 표나 strategy로 바꾼다

- 한 변수의 값(방법 이름, 명령 이름, 상태 문자열)마다 동작을 고르는 if-elif가 길게 늘어지고, 새 값이 생길 때마다 분기를 더하게 되는 곳을 지적한다. 이런 곳은 dispatch table(값에서 함수로 가는 dict)로 바꿔, 새 값은 표에 한 줄을 더해 넣는다(OCP: 확장에는 열려 있고 수정에는 닫혀 있다).
- 값의 집합은 `Literal`이나 `Enum`으로 타입에 두고 표의 키와 맞춘다. 잘못된 값은 경계에서 막는다.
- 구현마다 상태(학습한 모델, 설정)나 여러 단계(fit, predict)가 있어 함수 하나로 담기 어려우면 strategy pattern(같은 `Protocol`을 따르는 클래스)을 검토한다. 함수 하나로 충분하면 클래스를 만들지 않는다.
- if-elif로 두는 경우: 조건의 순서 자체가 비즈니스 규칙인 분기(예: 이기면, 지면, 그 밖에는), 갈래가 적고 늘어날 일이 없는 분기.

## C3. 함수 하나는 한 단계를 맡는다

- 단계는 읽기, 검증, 계산, 기록, 내보내기다. 계산 함수는 파일이나 DuckDB를 열지 않고 값을 받아 값을 돌려준다.
- 함수가 한 화면(약 50줄)을 넘거나 지역 변수가 여러 단계를 거쳐 다시 쓰이면, 단계를 함수로 나눌 수 있는지 본다.
- 인자가 여럿이고 같은 묶음이 여러 함수에 함께 다니면 pydantic 모델이나 dataclass 하나로 묶는다(C1의 경계 구분을 따른다).
- 지적할 것: 계산과 I/O가 섞인 함수, 플래그 인자 하나로 서로 다른 일을 하는 함수.

## C4. 같은 로직은 src/uplift 한 곳에 둔다

- 실험 `run.py`, 분석 노트북, `scripts/`가 같은 계산이나 같은 읽기 코드를 따로 가지면 `src/uplift/` 함수로 옮기고 호출처를 모두 바꾼다.
- 새 함수를 만들기 전에 `src/uplift/`에 같은 일을 하는 함수가 있는지 찾는다.
- 지적할 것: 복사된 코드, 이름만 다르고 같은 일을 하는 함수, 기존 함수를 두고 새로 만든 함수.

## C5. 타입은 pyright가 확인할 수 있게 쓴다

- 공개 함수의 인자와 반환에 타입을 적는다.
- `Any`, `cast`, `# type: ignore`는 라이브러리 타입 정의의 한계일 때만 쓰고, 그 한계를 한 줄로 적는다.
- 지적할 것: 타입 오류를 `cast`나 `ignore`로 덮은 곳, 같은 값이 함수마다 다른 타입(문자열과 Enum)으로 다니는 곳.

## C6. 실패를 숨기지 않는다

- `except Exception`이나 맨 `except`로 예외를 잡아 넘기지 않는다. 잡는다면 처리할 수 있는 구체적 예외만 잡는다.
- 실패를 `None`, 빈 표, 기본값으로 바꿔 돌려주지 않는다. 호출처가 실패를 모르고 다음 단계로 간다.
- 외부 명령(`subprocess`, Kaggle CLI, git)은 `check=True`로 돌리거나 종료 코드와 출력을 검사한다.
- 지적할 것: 삼킨 예외, 실패를 정상 값으로 바꾼 반환, 종료 코드를 보지 않는 외부 명령.

## C7. 같은 입력이면 같은 결과가 나온다

- 난수는 seed를 인자로 받아 `np.random.default_rng(seed)`처럼 그 자리에서 만든다. 전역 난수 상태를 쓰지 않는다.
- 결과가 행 순서에 기대면 정렬 기준을 명시한다(`sort_values`, `sort_index`, `kind="stable"`). set, dict, groupby 순서에 기대지 않는다.
- 결과를 바꾸는 값(seed, 문턱, 반복 횟수)은 코드 상수가 아니라 실험 `config.yaml`에 둔다.
- 지적할 것: seed 없는 난수, 순서에 기댄 결과, 코드에 박힌 실험 설정값.

## C8. 테스트는 바꾼 동작을 확인한다

- 직접 쓰거나 바꾼 분기, 반복문, 파서마다 테스트가 있는지 본다. 테스트 도입 순서는 `tests/CLAUDE.md`를 따른다.
- 기대값은 구현과 같은 식으로 다시 계산하지 않는다. 손으로 구한 값이나 효과를 심은 합성 데이터로 정한다.
- 지적할 것: 분기 하나만 지나는 테스트, 구현을 복사한 기대값, 실패할 수 없는 테스트.

## C9. 데이터프레임 코드는 행을 잃거나 섞지 않는다

- 고객 단위로 합칠 때는 `customer_id`로 `merge`나 `reindex`를 하고, 위치(`to_numpy()` 순서)로 맞추지 않는다. 합친 뒤 행 수가 기대와 같은지 본다.
- 열 이름을 여러 곳에서 문자열로 되풀이하면 상수나 모델 필드로 둔다.
- 반복문으로 행을 도는 계산은 벡터 연산으로 바꿀 수 있는지 본다. `inplace=True`와 chained assignment는 쓰지 않는다.
- 지적할 것: 위치로 맞춘 결합, 행 수를 확인하지 않은 merge, 행 단위 반복문.

## C10. 이름은 도메인 말을 쓴다

- 변수와 함수 이름은 `docs/glossary.md`와 기록 문서가 쓰는 말(정책 가치, 고른 정책, 발송 비율)을 따른다. 같은 대상을 파일마다 다른 이름으로 부르지 않는다.
- 주석은 `~/.claude/rules/code.md` 테스트와 주석 절을 따른다. 우회를 설명하는 주석이 필요해 보이면 원인을 고친다.
- 지적할 것: 같은 대상의 이름이 파일마다 다른 곳, 뜻을 알 수 없는 약어, 우회를 설명하는 주석.
